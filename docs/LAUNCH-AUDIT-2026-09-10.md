## Medicare appointment implications

The April 6, 2026 final rule is effective June 1, but its first page states that new marketing and communication policies apply to CY2027 marketing beginning **October 1, 2026**. This distinction matters on this audit's September date. The amended SOA rule removes the fixed 48-hour wait but retains prior agreement/recording and requires written SOAs for in-person personal marketing appointments. Do not indiscriminately remove the older waiting workflow for 2026 coverage. Confirm transition handling with the responsible carrier/upline contact. [Final rule, page 1 and SOA discussion](https://www.govinfo.gov/content/pkg/FR-2026-04-06/pdf/2026-06600.pdf)

The rule limits the Medicare appointment to the agreed health-related scope and prohibits marketing non-health products, including annuities, during that appointment. Keep Medicare and life/annuity discussions separately requested and arranged; a general retirement label must not silently expand an appointment's scope. [42 CFR 422.2264(c)(3)](https://www.ecfr.gov/current/title-42/chapter-IV/subchapter-B/part-422/subpart-V/section-422.2264)

The amended Part D disclaimer rule distinguishes TPMOs selling for all sponsors from those selling for fewer; its multi-sponsor applicability provision remains. It requires prominent website placement and electronic conveyance. The code needs accurate facts and the version appropriate to the marketing period, not only non-null numbers. [42 CFR 423.2267(e)(41)](https://www.ecfr.gov/current/title-42/chapter-IV/subchapter-B/part-423/subpart-V/section-423.2267)

## Security and reliability findings

- **Form protections:** Complete inquiries have a body-size limit, source/topic validation, normalized US phone numbers, exact permission wording/version checks, a honeypot, and command-center deduplication. The command-center connection cannot retrieve the prospect list. Preserve these controls.
- **Spam protection:** `lib/rateLimit.ts` now bounds its process-local storage and uses Netlify's connection IP instead of visitor-supplied forwarded headers, including when only Netlify's documented runtime environment values are present. Configured Turnstile verification now rejects network, HTTP, and malformed-response failures; unconfigured local forms remain usable. Capture failures return a truthful retry/contact response. Process-local limits still do not cover other server instances; production Turnstile and platform abuse controls remain necessary. [Netlify client-IP guidance](https://answers.netlify.com/t/is-the-client-ip-header-going-to-be-supported-long-term/11203), [runtime environment](https://docs.netlify.com/build/functions/environment-variables/), [Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)
- **Ad-platform privacy:** `lib/metaCapi.ts` now strips query/fragment data, accepts only the configured site origin and a small set of neutral page paths, skips other events, and omits service categories. It does not invent a replacement source page. No tracking credentials were enabled. Hashing contact details does not make those events anonymous: identifiers remain matchable. Confirm applicable data-sharing permission, platform restrictions on health/financial data, disclosure, and opt-out handling before any future activation. Permission to contact Christian is not assumed to be permission for every advertising data use. Internal campaign attribution remains unchanged and does not require a pixel.
- **Notification truthfulness:** `lib/notifyLead.ts` says the visitor has already received an email before the parallel send result is known, and promises a one-business-day personal response. Root is correcting that copy. Provider acceptance is not inbox delivery. Add delivery-failure handling and suppression before any automated nurture sequence.
- **Contact restrictions:** A restricted/ambiguous command-center match suppresses the immediate prospect reply. Imported monthly lists are not automatic permission for texts, calls, or marketing sequences. Preserve topic-specific permissions and opt-out records when adding calendar workflows.
- **Calendar events are not attendance:** Cal's meeting-start/end events can fire at scheduled times. Do not count elapsed time as a attended consultation or revenue. Use explicit attendance/outcome evidence, preserve stable booking identity, and deduplicate retries. Verify Cal signatures against the raw request bytes. [Cal webhook documentation](https://cal.com/docs/developing/guides/automation/webhooks)

## Netlify migration

Netlify's current adapter supports Next.js App Router, route handlers, image optimization, and server rendering. Keep `WEALTH_PREVIEW` unset for the production build so output uses the normal `.next` directory. Deploy with the maintained adapter rather than pinning a legacy Next runtime. A real deployment must still verify capture routes, headers, metadata, redirects, and image output. [Netlify Next.js support](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/)

`vercel.json` schedules only a Vercel cron; Netlify will not adopt it. The legacy enrollment-reminder route also depends on a separate database schema. Leave that feature inactive until a supported scheduler, permissions, deduplication, cancellation handling, and sender are actually connected. Cal's appointment reminders are a separate workflow.

Netlify Free pauses projects when the account's credit allowance is exhausted. Enable usage notifications and check remaining credits before advertising. Free hosting is a sensible pilot cost choice, but not an unlimited or guaranteed-availability service. [Netlify billing behavior](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/billing-faq-for-credit-based-plans/)
